Версия 2.0 от 21.09.2026. Источник обязательств: [TASK.md](../TASK.md),

<a id="scope"></a>
## 1. Продукт и границы

Поток: ручной текст/URL → анализ → сохраняемый инцидент → объяснение и предупреждение
→ проверка демонстрационного перевода → серверное решение → итог симулятора.
Обычный аккаунт даёт доступ к своей истории с разных устройств. Финансовые профили
и операции синтетические. Анализ не устанавливает факт преступления.

Обязательны собственный размеченный текстовый набор, TF-IDF + логистическая регрессия,
правила, URL-анализ, имеющийся реестр угроз, поведенческие признаки, карточки,
история, JSON-экспорт, 15 примеров и фактическое UX-исследование.
Распознавание происхождения звонка, медиа/CV, граф угроз, ресурсные заявки,
внешние банковские операции и встроенная платформа исследований исключены.
Речь поступает только готовой текстовой расшифровкой. Произвольные сайты не загружаются.

## 2. Стек и зависимости

Python 3.11/FastAPI/Pydantic, SQLAlchemy/Alembic/SQLite; TypeScript/React/Vite.
Для ML добавляется scikit-learn при отдельной реализации, с фиксацией версии.
Backend запускается в существующем `/Users/Shared/github/MachineLearning/ml_venv`.
Зависимости и обучение относятся к этапу ML, а не к подготовке документации.

| Слой | Допустимые зависимости |
| --- | --- |
| domain | stdlib, собственная фича, domain/shared |
| application | domain, application DTO и порты; сквозные workflows координируют публичные use cases |
| infrastructure | application-порты, domain, библиотеки реализации |
| transport | application и HTTP-схемы; без ORM и выполнения бизнес-политик |
| bootstrap | сборка всех реализаций; бизнес-слои его не импортируют |

Domain-фичи не импортируют друг друга. Application-фичи не вызывают внутренности
соседних фичей. SQLAlchemy/Pydantic/ML-объекты не пересекают внутренние границы.
Web: app → pages → features → shared; запрет прямых импортов между features.
Backend определяет риск и разрешённые действия; frontend представляет результат.

## 3. Расположение и форматы

Сохраняются `apps/backend/src/alpha_defense/{domain,application,infrastructure,transport,bootstrap}`
и `apps/web/src/{app,pages,features,shared}`. Фичи — identity, communications, detection,
incidents, protection, transfers, threats, education; scenarios — application workflow.
Исследование живёт в `research/` и `docs/research/`, без обязательной runtime research-фичи.
Будущие offline-команды данных и обучения — `scripts/ml/`, наборы — `datasets/text/`,
артефакты — `artifacts/text/`; до выполнения соответствующих карточек их наличие не заявляется.

JSON Schema и HTTP-контракты — `contracts/`; synthetic fixtures — `fixtures/`;
policy/guidance/education/trusted catalog — `content/`; runbooks — `ops/runbooks/`.
Общего utils/services/BaseService для несвязанных обязанностей нет.
Python — snake_case, TypeScript — принятые правила текущего дерева, UI — русский.
Используются действующие lint/format-конфигурации; описания API генерируются из backend.

## 4. Ответственность фичей

<a id="feature-identity"></a>
### Identity

Существующие demo-сессии остаются проверенным техническим основанием. Новая Account
получает устойчивый user_id, уникальный нормализованный login, password_hash и статус.
Хеширование пароля — через специализированную библиотеку в инфраструктуре, без
самописной криптографии. Порт credential verification не зависит от HTTP.
Регистрация не принимает роль; вход создаёт новую сессию владельца; logout отзывает
её. CSRF, HttpOnly/SameSite, Secure при HTTPS, rate limit входа обязательны.
Ни пароль, ни сырой session token не пишутся в логи/экспорты.

Workspace принадлежит user_id; session_id обозначает конкретный вход. Повторный
вход не создаёт второго владельца и не лишает доступа к старым проверкам.
Namespace продолжает изолировать manual workspace и scenario runs. Старые anonymous
runs автоматически не присваиваются произвольному аккаунту. Миграция сохраняет
существующие гарантии и имеет отдельные restart/ownership-тесты.
Account recovery по почте и сторонний вход не являются обязательными функциями.

<a id="feature-communications"></a>
### Communications

Сохраняются tagged-варианты SMS/chat/transcript/web, immutable raw-content,
версионированная нормализация и дедупликация source event внутри namespace.
Текст от пользователя недоверенный, не является инструкцией серверу.
В обучающий набор пользовательские runtime-сообщения автоматически не включаются.

<a id="feature-detection"></a>
### Detection и обучаемый анализатор

Порты возвращают plain results, сигналы, applicability/status и версии. Обученная
модель — инфраструктурный адаптер текстового порта; правила — отдельный анализатор.
ML-выход хранится отдельно от эвристического risk score. Backend policy объединяет
сигналы и объясняет, какие основания использованы. Нельзя приписывать модели
конкретный признак давления, если он обнаружен только правилом.

Минимум 400 уникальных синтетических текстов с двумя классами; целевое наполнение
около 200/200. Схема записи: id, text, label, template_group, source_kind,
annotation_note, dataset_version. Классы и спорные случаи определены инструкцией.
Перефразировки и близкие дубли группируются до разделения. Схемы представлены
разными независимыми группами; негативные примеры включают нейтральные упоминания
кодов, срочности и переводов. Примеры S01–S15 не служат обучающими метками.

Групповое разделение примерно 60/20/20 с проверкой наличия обоих классов в каждой
части. Сохраняются split manifest, seed и hash набора. TF-IDF fit только на train;
порог и небольшое число настроек выбираются на validation. Test открывается после
фиксации конфигурации; последующая правка требует нового независимого теста либо
явного признания, что прежний test стал validation. Rules/model/combined сравниваются
на одном test: precision, recall, F1, confusion matrix, размеры и ошибки.
Числа не переносятся на население; качество на synthetic-наборе ограничено его дизайном.

Артефакт содержит vectorizer/model, версии библиотек, dataset/split hash, threshold,
model_version и model card. Загружаются только доверенные локальные артефакты;
пользовательская загрузка сериализованной модели запрещена. Training — офлайн на CPU.
Неизвестные токены, пустой вектор, неверный язык и сбой модели имеют явные ограничения.

<a id="feature-incidents"></a>
### Incidents

Сохраняются P10: корреляция по явной связи и нормализованным индикаторам внутри
owner/namespace, но не одной временной близости; новый вход немедленно повышает
namespace ingress_risk_epoch, релевантное свидетельство — context_version.
Дубль source event не повышает версии повторно. До финализации остаётся pending.
Assessment immutable; перепроверка добавляет новую версию. История читает только
данные владельца, с pagination. Выбор явно связанного инцидента проверяется сервером.

<a id="feature-protection"></a>
### Protection

Предупреждение связано с конкретной оценкой. Dispatched, фактически presented и
ответ пользователя различаются; повтор не создаёт второе действие. Предупреждения
внутри приложения не зависят от согласия на UX-исследование. Закрытие окна не
разрешает запрещённый перевод. URL показывается безопасным текстом без перехода.
ResourceGate, заявка на закрытие сайта и внешний уведомляющий провайдер не нужны.
P13 реализовала внутреннюю сохраняемую warning-модель и inbox-границу с отдельными
состояниями dispatch/presentation/response. Публичное создание вместе с сохранённой
assessment и фактический экранный показ остаются задачами P15/P16.

<a id="feature-transfers"></a>
### Transfers

Профиль использует только завершённые синтетические операции до текущего перевода.
Начальное правило: история за 90 дней, не менее 10 операций для медианного сравнения;
меньший объём даёт insufficient_data. Новизна получателя и отклонение суммы —
признаки необычности, не доказательство мошенничества. История текущего перевода
не используется для оценки его самого. Версии профиля/истории входят в check.

Симулятор синхронный, все эффекты локальны одной SQLite БД. Проверка актуальности,
уникальность исполнения, запись fake bank operation, итог intent и audit атомарны
в одной UoW. Отдельные domain-модели check, intent и bank result сохраняются.
Нет внешнего вызова, accepted/processing и reconciliation. При crash транзакция
либо зафиксирована целиком, либо откатывается; повтор получает сохранённый итог.

<a id="feature-threats"></a>
### Threats

Сохраняется реализованный версионированный файловый реестр: атомарная публикация
проверенного снимка, происхождение, срок пригодности, exact match/no match/unavailable.
Граф и network analyzer не применяются и не ухудшают completeness своим отсутствием.

<a id="feature-education"></a>
### Education

Сохраняется P12: проверенный русский контент, mapping reason codes → рекомендации
и карточки, версионирование и безопасный fallback. Guidance не порождает исполняемые
команды, server allowed_actions не изменяются текстом. Контакт помощи берётся только
из trusted catalog. Свободный чат не требуется.

<a id="feature-scenarios"></a>
### Scenarios

Каталог подставляет synthetic inputs в обычные формы. Отдельный run/namespace,
восстановление после refresh и reset в новый run обязательны. Старые результаты
не удаляются reset. Expected остаётся в тестовом harness, не передаётся модели,
политике или UI участника. Универсальный язык сценарных шагов не нужен.

<a id="feature-research"></a>
<a id="technical-branches"></a>
### Research и технические ветки

Исследование — процедура и обезличенные наблюдения вне пользовательского runtime.
Результаты агрегируются воспроизводимым скриптом/ноутбуком, исходные ответы хранятся
приватно. Bootstrap собирает порты; существующие UoW/idempotency/audit/outbox
сохраняются. Новый экспорт пользователя принадлежит application/incidents,
сериализация — infrastructure; исследовательский экспорт с ним не смешивается.

## 5. Контракты и риск

UUID runtime IDs; время RFC3339 UTC, отображение Europe/Moscow; JSON UTF-8.
Money — integer amount_minor и RUB, положительная сумма до 100 000 000 копеек;
float запрещён. Реализованные ограничения размеров остаются действующими.
Схемы v1 из contracts сохраняются до явного версионированного изменения.

Assessment хранит owner/namespace, context_version, analysis plan, signals, reasons,
severity, completeness, score_kind, версии policy/model/content/registry/fixtures.
`complete` означает выполненные применимые проверки, а не безопасность.
Для текста в итоговой версии применимы ML + rules и lookup найденных индикаторов;
для URL — URL rules + lookup; для перевода — behavior + recipient lookup и явно
выбранный контакт. Нет индикатора/контакта — not_applicable; отказ требуемого
компонента или недостаток истории — partial/unavailable, не not_applicable.

Начальные границы heuristic score P11: low 0–24, medium 25–49, high 50–79,
critical 80–100. Это не probability. При полном отсутствии анализа — unknown,
unavailable, score=null. Отказ ML при работающих правилах — явная частичная оценка.
Новые ML-сигналы и их вклад фиксируются в policy v2 отдельной M03 до test-оценки;
P11 не переименовывается задним числом в обученную модель.

| Результат | Решение по переводу |
| --- | --- |
| low + complete | allow, требуется явное подтверждение пользователя |
| medium + complete | confirm, дополнительное подтверждение текущего предупреждения |
| high | hold, отправка запрещена; разрешены отмена и перепроверка |
| critical | deny, отправка текущего намерения запрещена |
| unknown или partial при low/medium | hold до пригодной повторной оценки |

TransferIntent: draft → checked → executed либо cancelled; hold/deny — решения check,
не утверждение, что внешний банк удерживает деньги. Изменение draft повышает revision.
Check связан с fingerprint, context_version, ingress epoch, версиями истории, policy,
model и registry; TTL не более 120 секунд и не дольше пригодности свидетельств.
Cancel допустим для ещё не исполненного своего intent независимо от pending анализа.

## 6. Согласованность и восстановление

Приём атомарно сохраняет наблюдение/инцидент/pending и версии. Анализ выполняется
вне долгой транзакции. Перед сохранением assessment проверяется актуальность
контекста; устаревший результат не снимает pending нового свидетельства.
Публикация assessment, warning, audit/outbox и финализация pending согласованы.

POST/PATCH команды требуют CSRF и Idempotency-Key. Область ключа включает actor,
namespace, method и route; один ключ с другим payload → conflict. Первичный вход
использует pre-session защиту, не клиентскую роль. У исполнения дополнительно
DB-уникальность по intent/revision: две вкладки с разными keys не удваивают эффект.

Перед исполнением сервер атомарно сверяет check, fingerprint, revision, owner,
epoch/context и отсутствие pending. Истёкший check требует проверки. SQLite
сериализует конкурирующие записи; in-memory воспроизводит ограничения. Outbox
доставляется at-least-once, повтор handler идемпотентен. Денежный demo-эффект не
делегируется повторяемому уведомлению. Секреты и raw-content не попадают в события.

## 7. HTTP и порты

Только реализованные маршруты публикуются в OpenAPI. Сейчас это health, session,
demo-session, consents и education list/detail — семь маршрутов в committed contract.
Новые account/auth, observations/incidents/assessments, profiles, transfers,
scenario runs и export добавляются соответствующими карточками вместе с DTO,
Problem Details, ownership/contract-тестами и генерируемыми web-типами.
Не публиковать работающие stubs для ещё не реализованной функции.

API остаётся `/api/v1`, ошибки в существующем формате, trace/request ID без секретов.
Порты: repositories/UoW, content, threat lookup, text/URL analysis, credentials,
clock/IDs, notification, demo bank, export serialization. Domain не читает файлы
моделей, контент или БД. Локальная модель не получает полномочий выполнять перевод.

## 8. UI и конфигурация

Экраны: вход/регистрация, ввод текста, URL, профиль, операция, результат/история,
карточки и каталог примеров. Везде loading/error/empty и ограничения оценки.
Русские подписи, money/date formatting, клавиатура, focus и читаемость предупреждений.
Не показывать опасный HTML; JSON-экспорт только своего assessment по allowlist,
без пароля, session token и исходного сообщения. Включаются schema_version,
assessment ID, время, scope demo, результат, причины, рекомендации и версии.

Пути каталогов/модели, БД, secret, execution mode и версии задаются backend settings.
Readiness проверяет обязательные файлы и БД; итоговая ML-конфигурация проверяет
доверенный совместимый артефакт. При сбое после старта запрос получает degraded,
а не вымышленный успех. CORS ограничен, HTTPS необходим при доступе извне.

Это тестовые случаи; они не заменяют десять пользовательских сценариев ПС-01–ПС-10.
Коды сохраняются, но изменённый стимул получает новую fixture_version; старые отчёты

## 10. Исследование

План аудитории и объёма задан заявкой: опрос 20, интервью 5, UX 10. Это цели набора,
не фактические наблюдения. До сессий фиксируются согласие, условия, набор заданий,
версии сборки/модели/политики/fixtures и основной trial каждого участника.
Метод ручной: лист наблюдения и анкета; для времени допустима запись экрана с
согласием либо заранее проверенный таймер. Нет требования писать study API.

Основные показатели: доля добровольно изменивших рискованное намерение среди
участников с измеренным prior intent и доступным выбором; время от реально видимого
предупреждения до безопасного действия; полезность 1–5 с числом ответивших.
Ack, чтение карточки и auto deny не доказывают изменение поведения. Без prior intent
показатель называется долей безопасного выбора. Окно 120 секунд, незавершённые
наблюдения, технические сбои и исключения задаются до сбора; нулевой знаменатель
даёт «нет данных», не 0%. Время без реакции не становится нулём.

Raw ответы/видео вне Git, публичны обезличенные агрегаты и методика. Не объединять
незаметно разные версии продукта или повторные trials одного человека. После
существенной доработки UX-выводы относятся к протестированной версии; новая версия
требует дополнительной проверки либо явного ограничения переноса результатов.
Исследование не доказывает снижение преступности или реальных финансовых потерь.

## 11. Хранение и эксплуатация

Один API-процесс и SQLite, короткие транзакции, миграции и backup/restore.
Существующие технические таблицы сохраняются. Добавляются accounts/credentials,
устойчивое владение workspace, assessments/warnings, profiles/operations/checks
и scenario runs по мере реализации, а не заранее пустыми модулями.
Пользовательская история не очищается reset; сроки удаления отдельно документируются.

Целевые среда и ресурсы заданы заявкой и должны быть проверены; это не измеренные
минимумы. Цели v1 по задержкам сохраняются для локальной приёмки: p95 сохранения
оценки ≤2 s, доставки готового предупреждения до показа ≤1 s, transfer check ≤2 s.
Измерять на указанном стенде с n, версиями и cold/warm-условиями; при невыполнении
цель явно пересматривается с причиной, не объявляется выполненной. Deadline анализа
1500 ms — начальная настройка, подлежит согласованию с обученной моделью.

## 13. Порядок реализации и приёмка

Реализация и обучение выполняются отдельными задачами по [плану v2](IMPLEMENTATION_PLAN.md). Для фичи обязательны domain/use case/adapter/HTTP и UI-проверки по её границе,
актуальные контракты и журнал evidence. Done только после приёмки. После каждой
завершённой карточки обновляется defense-guide только фактическими результатами.

Техническая готовность требует всех ФТ и пользовательских сценариев, всех Sxx,
проверки межаккаунтного доступа, второго устройства, перезапуска, экспорта,
отложенной оценки классификатора и воспроизводимого запуска. Полная сдача добавляет
реальное UX-исследование, отчёт, видео и презентацию. Готовность каждого этапа
подтверждается результатами проверок и соответствующими материалами.
